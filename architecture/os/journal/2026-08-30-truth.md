## Corrections

- **Apparent main force-push, actually a stale shallow ref.** On
  `git fetch origin main`, git reported `origin/main` "forced-update" from
  `17b7dbaa` (dated 2026-08-23) to `45d2b28` (today), and `git merge-base`
  between the two returned no common ancestor within the shallow (`depth
  50`) history — the shape of a rewritten branch. Before touching anything,
  checked `git ls-remote origin` (confirms `45d2b28` is genuinely
  `refs/heads/main` on GitHub right now) and `git log --oneline --all`
  (shows an unbroken, ordinary chain of audit/truth-cycle commits behind
  `45d2b28`, 58 commits ahead of `17b7dbaa` with normal cadence and no
  gap). Conclusion: no rewrite occurred. The container's local
  `refs/remotes/origin/main` was simply never refreshed past an early
  shallow clone (`17b7dbaa`, 2026-08-23) even though the detached-HEAD
  checkout it started from (`45d2b28`) was already current — an
  environment/caching quirk, not a repo-integrity incident. Fixed with
  `git checkout -B main origin/main` after the tree was confirmed clean
  (no local work at risk). Recorded here because the failure mode this
  layer is built to catch — a rewritten `main` — looks identical at first
  glance to this shallow-clone artifact, and future cycles hitting the same
  "forced-update" message should check `ls-remote` + full ancestry before
  assuming either an incident or a false alarm.
- The self-referential line count `inventory.json` records for its own path
  is `0` (the shell's `>` redirection truncates the destination file before
  the scanner reads the tree, so the scanner sees itself as empty). Noted
  after an initial dry run to `/tmp` — which does *not* truncate the real
  destination first — produced a misleading ~61k-line "delta" against the
  committed file purely from that methodology difference, not real drift.
  Re-ran the real commands against their real destinations to get the true
  (small, explainable) delta reported above.
