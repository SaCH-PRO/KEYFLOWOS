## Corrections

- **Local `main` ref is stuck at an old baseline (`bd26a0d6`) independent of
  the detached-HEAD checkout.** Before step 1, `git status` showed HEAD
  detached at `31f787f2` — already equal to origin's tip — while the local
  `main` branch pointer was still at `bd26a0d6`, a commit from well before
  even the 2026-08-31 truth cycle. `git checkout main && git pull --ff-only`
  fast-forwarded through 31 commits' worth of history and printed a large
  file-list diff (reaching back to 2026-08-31 journals, `deploy-prod.ps1`,
  `docs/KEYFLOWOS_APP_SPEC.md`, etc.) — at first glance this looked like it
  might mean 31 commits of *new* content had just landed in the working
  tree since the last cycle. It hadn't: the detached HEAD was already at the
  tip, so the working tree was unchanged by the pull; only the `main` ref
  itself moved. This appears to be a property of how this container image
  was baked (local `main` frozen at a stale snapshot, refreshed only by
  fetch/pull, never by a push from inside the container) rather than
  anything a cycle did wrong. Caught before it produced a wrong Deltas
  narrative by diffing inventory.json against the *last truth commit's own
  committed copy* (`168732d0`) rather than trusting the pull's file list —
  that gave the correct, much smaller attribution (5 files / 325 lines, not
  31 commits' worth).
- **The inventory scanner's self-referential entry needs the exact
  playbook-specified redirect, not a side-by-side comparison file.** A first
  pass ran `inventory.py > /tmp/inventory_new.json` (a safety habit, to diff
  before overwriting) and got a confusing +62,336-line delta traced to
  `architecture/inventory.json`'s own entry: 61,511 lines / 1.59MB in the
  `/tmp`-redirected run vs. 0/0 in the committed file. This is not drift or
  a race condition — it's because the shell's `>` redirect truncates its
  destination file to empty *before* python starts scanning, so the real
  command (`... > architecture/inventory.json`) always sees itself as 0
  bytes mid-run, while redirecting to a different path lets the scanner see
  the real, un-truncated (and much larger) file still sitting on disk. Fix:
  ran the exact command from the playbook, direct to
  `architecture/inventory.json`, which reproduced the expected 0/0
  self-entry and the correct, small, fully-attributable delta. Noting this
  here so a future cycle doesn't waste time chasing a phantom "session file
  suddenly 1.5MB" lead — checked that first too (`.claude/coordination/
  sessions/<uuid>.json`, briefly suspected as the culprit) before finding
  the real cause was the scanner's self-reference, not the session file
  (which was a clean, net-zero rename both times).
