## 1. Why this exists

CF-33 (P0): the trust census was never refreshed after 2026-09-28, so release law (census section 4) could not be checked against what is built. The law says that before production release no T0 or T1 domain may be UNASSESSED, every T0 domain must be PROVEN_AT_DECLARED_SCOPE or EXTERNALLY_VERIFIED, and every catastrophic-failure scenario needs a disposition. This file refreshes the census for Release 0 (issue #186, seven steps, plus the customer link and receipt that D-07 put in scope). It changes no recorded state. The matrix and the register stay as adopted. Each row proposes a state or disposition, and the owner of record accepts or rejects it.

## 2. How to read the tables

- **Recorded:** the state in the matrix as adopted on 2026-09-28.
- **R0 touch:** `yes` when a Release 0 step reads, writes, or depends on the domain; `no` when only surfaces outside the journey do. A `no` row still counts for release law, because those surfaces ship in the same server.
- **Evidence:** the test files on this base that exercise the domain, in backticks. `OPEN` marks a gap that no test covers. Every backticked path is checked to exist and to be a test file by `apps/server/test/log-redaction.integration.test.ts` (section "Release 0 trust census"). Run a cited test to see it pass; this file does not claim a run.
- **Proposed state:** a value from the matrix's `allowed_states`, at the Release 0 scope, pending owner acceptance.
- **Disposition:** required on every T0 domain row and on every scenario row. The values are the register's `allowed_dispositions` plus one:
  - `PREVENTED`, `DETECTED_AND_CONTAINED`, `RECOVERABLE`: a working control. Each must cite at least one test (the census check enforces this).
  - `TRANSFERRED`, `NOT_APPLICABLE`: as in the register.
  - `RELEASE_BLOCKING`: no disposition is supported by evidence at this base. Under release law the row blocks production release until proof lands, or until the owner rules it out of the Release 0 scope.
  - `ACCEPTED_RESIDUAL_RISK` is never proposed here. Only the owner of record can accept a risk, with an owner, rationale, expiry and compensating controls.
- A `-` in the Disposition column of a T1 or T2 domain row means none is proposed. Release law still requires those rows to reach PROVEN_AT_DECLARED_SCOPE or carry an owner risk acceptance.

## 6. Findings recorded by this packet

1. **Request URLs were logged whole (IA-044, CF-011, CF-029). Closed by V1-83 (FOLLOW3-C1-HTTP-LOG-ROUTE-PATTERN).** At bb6b86d4 `LoggingInterceptor` built its access line from `req.url` (`apps/server/src/core/interceptors/logging.interceptor.ts:22`), emitted at `:24` (slow requests), `:26` (debug) and `:31-33` (errors), and main.ts creates the app with no `logger` option, so Nest's default ConsoleLogger prints the debug level. The line carried every credential a URL holds. Customer credentials: the link token on the public invoice-link, receipt, pay and payment-intent routes, and the quote, export, order-status, preview and portal tokens. Platform secrets: the Chatwoot webhook secret in the path (`chatwoot.controller.ts:14`, POST /chatwoot/webhook/:secret), WHATSAPP_VERIFY_TOKEN in the query (`whatsapp.controller.ts:234-237`, hub.verify_token; the social webhooks take the same parameter) and OAuth authorization codes on the callback routes (for example GET /drive/callback?code=). The line now names the route pattern Express matched (`req.route.path`), else `<unrouted>`, and never the query; it keeps the method, the status, the duration and the correlation id. The real-database windows prove it on GET /commerce/public/invoice-link/:token, with and without a `?code=` query, and section 1b proves it for each platform secret on the success line and the error line.
2. **The 500 line logged request.url too (IA-044, CF-011, CF-029). Closed by V1-83.** At bb6b86d4 `GlobalHttpExceptionFilter` logged `Unhandled exception on <method> <request.url>` on every unhandled error (`apps/server/src/core/filters/http-exception.filter.ts:65`), and its error-registry label fell back to request.url when no route had matched (`:77`). The filter now uses the same helper as the access line (route pattern, else `<unrouted>`) for both. A real-database window injects a 500 into the token route and finds no token in any entry; section 1b calls the filter directly for each platform secret and for an unrouted request, whose path and query reach neither the line nor the registry label. The response body still carries `path: request.url`: that echoes the caller's own URL back to the caller, is not a log, and is a pinned contract.
3. **A SEND_EMAIL playbook logs the contact's email (IA-044, CF-029).** `AutomationExecutorService` runs the business's playbooks on contact.created and, for a SEND_EMAIL action, logs `Email sent to <email>` at log level (`apps/server/src/modules/flow/automation-executor.service.ts:286`; `:358` logs the phone for SEND_WHATSAPP). The suite mounts that listener, with the real ActivityService, on the production event bus options and seeds a SEND_EMAIL playbook: with the playbook the email reaches the logs, without it nothing does. The other contact.created listeners (flow/activity-event.listener.ts, flow/flow.listener.ts, ai/ai.listener.ts, growth-intelligence/journey-listener.service.ts, webhooks/webhook-dispatcher.service.ts) are not mounted; their log calls were read, not run, and interpolate no contact field. The fix is outside the write set. The case stays `it.todo` and names the file.
4. **Every pkt/* PR fails closed at Validate control artifacts (IA-048).** The gate now treats pkt/* heads as packet PRs (D-22). On a pkt/* branch, `.agent-control/active-packet.yaml` names an impl/* `implementation_branch`, and packet workers may not edit `.agent-control/`. So the branch check fails for every pkt/* PR, draft or not: the suite runs the step with bash against fixture artifacts and gets `::error::active-packet.yaml implementation_branch does not match PR head`. If the artifacts named the pkt/* head, a non-draft PR would still stop at the grant step: `evaluateGrantGate` refuses any head outside impl/* (`scripts/agent-control/lib/admission.mjs`, NOT_IMPL_BRANCH), and so do the autopilot's PR listing and `lib/events.mjs`. That fails closed, but every pkt/* PR now shows a red Agent Control Gate, and pkt/* PRs have no working admission path. The change is outside this write set.
5. **The gate is self-modifiable for pkt/* heads (IA-048, CF-023).** The gate runs on pull_request. It checks out the PR merge ref and runs the PR's own copy of the workflow and of `scripts/agent-control/auto-merge-admitted.mjs`. A pkt/* PR that edits either one (a script that exits 0, or a scope arm without `pkt/*`) gets a green gate with no #80 grant. For impl/* heads the trusted merger re-checks the grant from base code. It ignores pkt/* heads (`scripts/agent-control/lib/events.mjs`), so for pkt/* this gate is the only automated control. The root CODEOWNERS names the owner for every path, `.github/workflows/` included, but code-owner review binds only if branch protection requires it, and branch protection is a repository setting this census cannot see. The gate's tests prove its text and the behaviour of its scripts. They do not prove that a pkt/* PR cannot bypass it.
6. **Not found leaking:** no contact email, operator bearer JWT or derived providerPaymentId appeared in any log entry during recordPayment (with its keyed replay), contact create with no playbook configured (with its duplicate 409, and with the contact.created playbook listener mounted) or the public link view. The operator's bearer JWT did not appear in the playbook window either.
