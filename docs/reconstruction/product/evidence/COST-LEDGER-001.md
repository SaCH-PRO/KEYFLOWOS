## 1. The rule

Release 0 runs with **every optional provider off**. Each operation below either
stays off in Release 0, or, when a caller reaches it, **fails visibly and on its
own**: the request that needed it gets a clear answer, and nothing else breaks.
No Release 0 money route (invoice create and issue, manual payment, balance,
lists, receipt) needs any of them.

Columns:

- **Env var**: what turns the operation on. "Per business" means the business connects its own account (OAuth) or stores its own key (BYOK).
- **Code default**: what the code does when the variable is unset. `off` means the operation does not run until it is configured; `on` means it runs unless something turns it off.
- **Release 0**: the state Release 0 runs in.
- **Billing**: `paid` (metered by the provider), `free` (no charge; may have quotas), or `host` (part of hosting, not per call).
- **Failure mode**: what a caller sees when the provider is not configured or is down. **Proven** rows are pinned by the R0-07 and R0-07a suites; the others are read from code at the anchor and are declarations, not proofs.
- **Cost owner**: who pays. `Platform` is the KeyFlow operator's account; `Tenant` is the business's own account (its OAuth connection or BYOK key).

## 7. Follow-ups found by R0-07 (outside its write set)

1. **Done by R0-07a-AI-DIRECT-503 (bc6dfaba; tests first at 42ead2b7).** `AiUsageService` and `KeyCortexVoiceService` call OpenAI directly, so they did not get the gateway's structured 503. They now throw it themselves when no OpenAI key is configured, before any client, provider call or usage row (section 2). The proof is `ai-direct-provider-503.integration.test.ts` (real database, prefix `k07c_`), `ai-usage.service.spec.ts` and `key-cortex-voice.service.spec.ts`, bound by the `optional-services-fail-visibly.json` manifest. Items 7 and 8 are what R0-07a found outside its write set, and item 9 is what its review found there.
2. **Fixed by R0-CMF4-SEND-EMAIL-ORDER** (tests 913418a6, fix 9d776851, review repairs on top of 022f0604). `POST .../quotes/:id/send-email` moved a DRAFT quote to SENT before it sent (`commerce.controller.ts`), so a refused send answered 503 but left the quote SENT, with a view token and a `quote.sent` event, though the customer never got the email. The route now goes through `CommerceService.sendQuoteWithViewToken`. It reserves the DRAFT's view token before the send, as a compare-and-set on (DRAFT, no token): of two overlapping sends one writes it and the other mails the same token, and a "mark sent" made meanwhile keeps it. The public accept and reject routes refuse a DRAFT, and only the message being sent carries the token. A refused (503) or failed send (the transport throws, or Gmail answers an error: the old 400) clears the token it reserved while the quote is still that DRAFT, so the DRAFT is left with no view token (R2), no `sentAt`, no `quote.sent` event and no contact event. An accepted send moves the DRAFT to SENT as a compare-and-set (`updateQuoteStatus` `ifStatus: 'DRAFT'` with the token). A quote another request already moved to SENT with that token is left as it is (one `quote.sent`, one contact event, one `sentAt`); a quote rejected, accepted or given another token meanwhile is not overwritten, and the route answers 409 `quote_changed_during_send` with `emailSent: true`. A SENT quote, as in the R0-07 suite, is unchanged.
3. **Fixed by R0-CMF4-SEND-EMAIL-ORDER** (tests 913418a6, fix 9d776851, review repairs on top of 022f0604). `POST .../invoices/:id/send-email` created the invoice's payment link before it sent, so a refused send left a new PaymentLink row (no ledger rows, no status change). It now goes through `CommerceService.sendWithPublicInvoiceUrl`. An invoice with a live link (or a PAID or VOID one) gets the link `publicInvoiceUrl` hands out, unchanged: no row is created, so a failed send leaves none. For an invoice with no live link, the PaymentLink row is written before the send with a pending expiry (`PENDING_SEND_EXPIRY`, a value no `expiresInDays` gives). It is live, so a request made while the message is with Gmail (a second send-email, a reminder, `POST .../payment-link`, an automated email) hands out this one link instead of writing another, and `reissueLink` clears the pending expiry when it does. An accepted send clears it too, so it leaves exactly one live link with no expiry, the one in the email and the response (D-07), and a resend reuses it (V1-48). A refused or failed send deletes the row only while it is still pending and active, so it leaves none unless another request handed the link out meanwhile (the link is then that request's too) or the operator revoked it. Proven on a real database in the R0-07 suite (prefix `k07a_`, nine cases bound by `optional-services-fail-visibly.json`): with no Gmail connection (503), and with a connected business whose real GmailService drives a stubbed Gmail transport that throws, answers an error, or accepts. The review repairs add seven cases where another request lands while the send is with Gmail: an operator rejection is kept (409, no `quote.sent`, the emailed link cannot accept it); a second click or a "mark sent" leaves every emailed quote link opening the quote, with one `quote.sent`; a second invoice send shares the one live link, and revoking it closes both emails; a failed first send does not take away the token or link an accepted second send mailed.

   Still open, outside R0-CMF4's scope: (a) a live pre-V1-48 cuid token is still rotated before the send (ST-V48-1), and a failed send does not restore it, because putting back the guessable token would undo ST-V48-1 and a concurrent send may already have mailed the new one. (b) `POST .../invoices/:id/send-reminder` (`CommerceService.sendInvoiceReminder`) still creates a missing link before it delivers, so a refused reminder can leave a new PaymentLink row, as send-email did. (c) Correction (R0-CMF4 review SEC-CMF4-2/3, CR-CMF4-1): the 9d776851 text here said two concurrent first sends of an invoice could each write a working link and that the old order had the same quote race. For a second send made while the first was with Gmail, the old order had neither: the link or token was written before the send, so both emails carried it. The review repairs restore that and keep the failed-send guarantee. What is left is the find-then-create window `createPaymentLink` has always had (two requests within the same few milliseconds can each write a link), and a status change or bulk send that read the quote before the reservation and wrote after it, which the send now reports as 409 rather than overwriting. (d) The invoice route still flips DRAFT -> SENT from the invoice it read before the send, so two overlapping first sends both flip it: SENT -> SENT is an allowed no-op transition and the ledger posting is idempotent, but `invoice.sent` is emitted and logged twice, as on the base. (e) While a pending link exists its `expiresAt` reads 9999-12-31 in the operator's link list. That lasts one Gmail round trip, or stays if the process stops mid-send (the link then behaves as one with no expiry).
4. **Fixed by R0-CMF5-GMAIL-CONNECT-BINDING** (tests c788e635; R0-07 review ST-2). Gmail connect was not bound to the user who started it: the signed OAuth state named only the business, and `GET /commerce/gmail/callback` needs no login, so whoever completed Google consent on a forwarded auth URL linked their mailbox to that business in that one request. The state now carries the initiating user id, the business id, a nonce and a 10-minute expiry (HMAC-signed with `GOOGLE_STATE_SECRET`, single use per process as R0-07 made it). The callback stays public (Google redirects the browser, and the web proxy forwards no session, so this base has no session the callback could verify) and links nothing: for a verified state that names a user it exchanges the code and stores the tokens as a PENDING `connector_accounts` row (provider GOOGLE, service GMAIL, tokens encrypted, bound in `settings` to that user, business and nonce, 15-minute window; an existing table, no schema change), then redirects `gmail=pending&pending=<id>`. `POST /commerce/businesses/:b/gmail/confirm {pendingId}` activates it (writes `Business.gmail*`) only for that user, still the owner (or SUPER_ADMIN), on that business, inside the window, once; anything else is 404 `GMAIL_PENDING_NOT_FOUND` and links nothing. An expired, replayed, forged or user-less state redirects `gmail=error&reason=invalid_state` with no token exchange. Until the owner confirms, a mailbox already connected stays the one mail is sent from. Proven on a real database with Google's token exchange stubbed (`gmail-connect-binding.integration.test.ts`, prefix `k07d_`, and `gmail.service.spec.ts`, bound by `gmail-connect-binding.json`; 19 of 25 integration cases and 9 of 9 spec cases failed before the fix). The R0-07 suite's `it.todo` for ST-2 and ST-3 is now covered by that suite; retiring it needs `optional-services-fail-visibly.integration.test.ts`.

   R0-CMF5 review repairs (pkt/R0-CMF5-GMAIL-CONNECT-BINDING-repair) closed what the first pass left open, and four more gaps: (a) the owner confirms in the app: `/app/commerce?gmail=pending&pending=<id>` reads `GET .../gmail/pending/:id` (OWNER only, bound to the user the state names, returns the mailbox and no token), asks "Connect <email>?" and POSTs `{pendingId, email}`; the confirmation must name the staged mailbox (409 `GMAIL_PENDING_EMAIL_MISMATCH` otherwise), and the web shows a `GMAIL_OWNER_ONLY` refusal instead of reporting success.
