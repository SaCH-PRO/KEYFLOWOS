# KEYFLOWOS R&D Engine — External Intelligence and Convergence

Status: foundational contract
Scope: development/R&D plane; designed to become a KEY capability later.

## Purpose

KEYFLOWOS maintains one R&D process. Repository mining is an acquisition capability inside that process, not a competing research programme.

The R&D engine may ingest internal code forensics, operational evidence, experiments, papers, books, standards, reference systems, and open-source repositories. Source disciplines and provenance remain distinct until an explicit KEYFLOW convergence step.

## Canonical flow

SOURCE -> RAW EVIDENCE -> EXTRACTION -> GENERALIZED PRINCIPLE -> KEYFLOW MAPPING -> CONVERGENCE -> CANONICAL DECISION -> IMPLEMENTATION -> PROOF -> FEEDBACK

Research does not become architecture merely because it was discovered. External evidence may influence canonical KEYFLOWOS only through convergence.

## Research lanes

1. Internal R&D: maps, microscopic traces, journeys, constellations, kernels, causal/dynamic/feedback graphs, incidents, code and architecture forensics.
2. External R&D: primary literature, standards/specifications, engineering systems, reference implementations, and open-source repository intelligence.
3. Empirical R&D: tests, experiments, benchmarks, simulations, production/operational evidence.

These lanes preserve their source terminology, provenance, assumptions, confidence and limitations. They are synthesized only when answering a KEYFLOW research question.

## Repository intelligence

A repository mining run must capture source identity and exact revision, license/provenance, relevant implementation evidence, tests and operational patterns where available. It extracts small evidence-backed patterns rather than importing a repository's architecture wholesale.

Each candidate is mapped against existing KEYFLOW capabilities, journeys, kernels, contracts, findings, recommendations and code before proposing anything new.

## Convergence classifications

- SAME: strengthens evidence for an existing concept.
- SPECIALIZATION: improves or sharpens an existing concept.
- RELATED_DISTINCT: related but semantically separate.
- IMPLEMENTATION_ALIAS: different implementation/name for an existing semantic concept.
- HISTORICAL: useful provenance, not current architecture.
- GENUINELY_NEW: candidate new primitive requiring explicit review.
- CONTRADICTORY: conflicts with current evidence/contract and creates a contradiction item.
- LOW_VALUE: retain as reference only.
- UNSAFE_OR_INCOMPATIBLE: reject with reason.

Disposition is separately recorded as REFERENCE, INSPIRATION, ADAPT, ADOPT, REJECT or UNRESOLVED. ADOPT must be rare and requires license, security, architecture and test review.

## Promotion laws

1. External research cannot directly become canonical KEYFLOW architecture.
2. Before creating a new primitive, skill, runtime, state machine or abstraction, search for the semantic concept already present in KEYFLOWOS.
3. Preserve rejected and unresolved research with reasons so agents do not repeatedly rediscover discarded paths.
4. Working implementation evidence outranks marketing claims; conflicting claims and code evidence are retained separately.
5. A decision must remain traceable backward from implementation -> contract -> decision/recommendation -> convergence -> mapping -> extracted pattern -> source/revision/evidence.
6. No research-derived implementation is complete without proof at the relevant semantic seam; no fake green.
7. Tool-specific agents (ChatGPT, Claude Code, Kimi Code and future workers) consume the same canonical repository R&D state. Tool-specific instructions must not become competing sources of project truth.

PERCEIVE/QUESTION -> DISCOVER -> INGEST -> ANALYZE -> COMPARE -> DEDUPLICATE -> EXPERIMENT -> CONVERGE -> PROPOSE -> APPROVE/GATE -> IMPLEMENT -> VALIDATE -> MEMORY UPDATE
