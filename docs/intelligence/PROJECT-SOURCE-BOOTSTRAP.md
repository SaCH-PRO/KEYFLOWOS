## Mandatory startup protocol for every new KeyFlowOS chat

Before substantive KeyFlowOS analysis or implementation:

1. Access the GitHub repository `SaCH-PRO/KEYFLOWOS`.
2. Read `docs/intelligence/00-START-HERE.md`.
3. Follow the load order specified there.
4. At minimum read:
   - `docs/intelligence/01-MASTER-CONTEXT.md`
   - `docs/intelligence/02-SYSTEM-MODEL.md`
   - `docs/intelligence/03-ANALYSIS-MAP.md`
   - `docs/intelligence/04-CONCEPT-REGISTRY.md`
   - `docs/intelligence/05-DECISION-REGISTER.md`
   - `docs/intelligence/06-OPEN-QUESTIONS.md`
   - `docs/intelligence/07-CURRENT-STATE.md`
   - `docs/intelligence/handoff/CURRENT-HANDOFF.md`
   - `docs/intelligence/handoff/CURRENT-STATE.yaml`
   - the active journey/domain/investigation files referenced by current state.
5. Verify that the repository branch/commit being analyzed is current enough for the requested work.
6. Report a short Context Integrity Check before resuming a major analytical cycle:
   - active phase
   - active journey mesh/unit
   - last completed analytical state
   - current unresolved convergence
   - next action
   - any missing/contradictory context
   - `Context integrity: PASS` or `FAIL`
7. If required canonical context is missing, stop and recover it rather than inventing continuity.

## Persistence contract

Conversation is working memory only.

A material KeyFlowOS discovery is not considered preserved until it is written back to the repository intelligence layer.

After a substantial analytical cycle, update as appropriate:

- active journey/domain/investigation dossier
- concept registry
- decision register
- open questions
- findings register
- contradiction register
- recommendation register
- `07-CURRENT-STATE.md`
- `handoff/CURRENT-HANDOFF.md`
- `handoff/CURRENT-STATE.yaml`
- a dated session record

Then create a meaningful Git checkpoint.

Do not wait for a chat to approach its length limit before checkpointing.

## Evidence discipline

Always preserve:

`evidence -> interpretation -> decision`

Use or respect the following classes when material:

- ESTABLISHED FACT
- IMPLEMENTATION FACT
- TEST SOURCE
- GENERATED STATE
- MAINTAINED ARCHITECTURE DOC
- HISTORICAL / STALE DOC
- PRODUCT SOURCE
- ACCEPTED DECISION
- WORKING HYPOTHESIS
- OPEN QUESTION
- DEPRECATED / SUPERSEDED
- RECOVERY UNCERTAIN

Never silently convert an interpretation into a fact or accepted decision.
Never treat an old architecture document as current implementation truth.
Never treat current implementation behavior as automatically canonical architecture.
Never claim a test was run merely because a test file exists.

## Governing analytical rule

`MAP BEFORE MODIFYING`

For significant changes, identify the affected journeys, domains, capabilities, entities, events, authority model, invariants, tests and existing architecture seams before modifying production behavior.

Prefer strengthening an existing coherent seam over inventing a parallel `v2` architecture unless evidence shows the existing seam cannot serve the target model.
