# KeyFlowOS Multi-Agent Continuity Contract

Status: CANONICAL OPERATING PROTOCOL

This file exists so ChatGPT project threads, Claude Code, Kimi Code, Codex, and human collaborators all consume and contribute to the same durable KeyFlowOS intelligence.

## Prime rule

Conversation/session memory is temporary. Repository intelligence is durable.

Canonical intelligence lives under:

`docs/intelligence/`

No chat thread, model session, coding-agent context window, or private scratchpad is allowed to become the only location of a material architectural conclusion.

## Programme identity

The current programme is **not** a sequence of local fixes and is **not** an implementation-ticket factory.

We are constructing a progressively richer virtual architectural / causal understanding of the entire KeyFlowOS application from the real repository and product evidence, then repeatedly converging and re-auditing that model until it can support one comprehensive, directly actionable transformation plan for the real codebase.

Canonical operating loop:

```text
REPOSITORY / PRODUCT EVIDENCE
        ↓
MAP
        ↓
MICROSCOPIC TRACE
        ↓
JOURNEYS
        ↓
JOURNEY CONSTELLATIONS
        ↓
KERNELS
        ↓
DYNAMIC / CAUSAL / FEEDBACK GRAPHS
        ↓
STANDARDS / OSS / FRONTIER RESEARCH
        ↓
FINDINGS / CONTRADICTIONS / OPTIONS
        ↓
POOL
        ↓
TARGET SYNTHESIS
        ↓
BACKWARD RE-AUDIT
        ↓
REOPEN EARLIER JOURNEYS / KERNELS WHEN NEEDED
        ↓
REFINE / RE-POOL / RE-CONVERGE
        ↓
LOOP AGAIN AT A LARGER SCALE
```

The eventual output is a whole-system target architecture + migration architecture + proof architecture + sequenced code-level transformation programme.

Individual `KF-EXEC-*` packets may be drafted early as **falsification probes / implementation-shape evidence**, but they do not become the programme frontier unless the comprehensive analysis programme deliberately promotes implementation readiness.

## Context Integrity Check

Before resuming a major analytical cycle, establish:

- implementation branch + current implementation-evidence commit;
- code-bearing forensic baseline;
- intelligence branch + current intelligence commit;
- current programme phase;
- active journey mesh / constellation / pool;
- active kernels;
- last completed analytical tranche;
- most recent backward re-audit result;
- unresolved convergence questions;
- exact next analytical action;
- status of any drafted execution packets (POOLED / CANDIDATE / AUTHORIZED / IMPLEMENTED / PROVEN);
- missing or contradictory context;
- `Context integrity: PASS` or `FAIL`.

Never infer that an implementation packet is the active frontier merely because it is the latest-created artifact.

## Cross-thread continuity law

All ChatGPT project threads are treated as **ephemeral working views over one repository-backed programme**.

A new thread must not restart the analysis from first principles when durable state exists.

A thread may specialize temporarily in a journey, provider, kernel, migration question, standards study, or adversarial review, but its material output must return to the canonical repository intelligence and be re-ingested into the active pools/loops.

Cross-thread invariant:

> A useful conclusion from one thread must improve the shared virtual model available to every later thread.

Therefore:

```text
THREAD WORK
→ PERSIST EVIDENCE / CONCLUSION
→ UPDATE ACTIVE POOL / JOURNEY / KERNEL
→ REFRESH CURRENT + ROLLOVER
→ LATER THREAD LOADS DURABLE STATE
→ CONTINUES FROM EXACT FRONTIER
```

## Continuous rollover discipline

Do not wait for a context-limit warning.

After every material tranche that changes any of the following:

- active frontier;
- accepted target semantics;
- active journey/constellation/kernel set;
- pooled evidence;
- findings/contradictions/recommendations;
- migration direction;
- proof obligations;
- implementation-readiness status;
- major innovation direction;

refresh at minimum:

- `handoff/CURRENT-HANDOFF.md`
- `handoff/CURRENT-STATE.yaml`
- `handoff/NEXT-CHAT-ROLLOVER.md`
- `handoff/NEXT-CHAT-ROLLOVER.yaml`

and the relevant journey/kernel/investigation artifacts.

Preferred cadence:

```text
MAJOR TRANCHE
→ PERSIST CANONICAL RESULT
→ REFRESH CURRENT STATE
→ REFRESH ROLLOVER
→ ONLY THEN START NEXT BROAD TRANCHE
```

The rollover packet must always be sufficiently self-contained that a fresh thread can recover the programme if the current chat disappears after the next message.

## Chat-length risk protocol

There is no reliable numeric product cutoff to plan against. Therefore continuity is maintained proactively, not reactively.

When context-risk or compaction is suspected:

1. do not start another broad investigation;
2. finish the current atomic trace only;
3. persist its result;
4. refresh CURRENT + ROLLOVER;
5. record exact next action and active pool;
6. move to a fresh chat if necessary.

Emergency invariant:

> Never trade durable continuity for squeezing one more broad tranche into a nearly exhausted conversation.

## Persistence obligation

A materially important result is not complete until written into the correct repository intelligence artifact.

After substantial work, update as applicable:

- active journey / constellation / investigation dossier;
- active kernel(s);
- `04-CONCEPT-REGISTRY.md`;
- `05-DECISION-REGISTER.md`;
- `06-OPEN-QUESTIONS.md`;

## Evidence discipline

Preserve:

`evidence → interpretation → architectural implication → synthesis / decision`

Distinguish at least:

- IMPLEMENTATION FACT
- RUNTIME EVIDENCE
- TEST SOURCE
- EXECUTED TEST RESULT
- GENERATED STATE
- MAINTAINED ARCHITECTURE DOCUMENT
- HISTORICAL / STALE DOCUMENT
- PRODUCT SOURCE / VISION
- INFERENCE
- WORKING HYPOTHESIS
- ACCEPTED DECISION
- RECOVERY UNCERTAIN
- POOLED IMPLEMENTATION-SHAPE EVIDENCE

Do not claim tests passed unless actually executed in the relevant environment.
Do not treat historical plans as current implementation truth.
Do not treat current implementation as automatically canonical target architecture.
Do not treat a locally converged journey as permanently closed; later constellation/kernel evidence may reopen it.

## Governing architecture rule

`MAP BEFORE MODIFYING`

For significant behavior changes, identify affected:

- journeys;
- constellations;
- kernels;
- domains;
- capability contracts;
- principals / authority;
- data entities and mutations;
- state transitions;
- events / queues / jobs;
- external integrations;
- invariants;
- concurrency / idempotency boundaries;
- tests / proofs;
- legacy / compatibility consumers;
- migration dependencies.

Prefer strengthening coherent existing seams before creating parallel replacement architecture.

## Pooling and backward re-audit law

Local convergence is provisional until stressed by adjacent journeys and kernels.

When several related traces mature:

```text
RELATED JOURNEYS / FINDINGS
→ POOL
→ CROSS-KERNEL SYNTHESIS
→ TARGET CANDIDATE
→ BACKWARD RE-AUDIT THROUGH EARLIER JOURNEYS
→ KEEP / REFINE / REJECT / REOPEN
```

New evidence should be allowed to invalidate prior synthesis. This is expected programme behavior, not analytical failure.

## Innovation law

Standards, best practices, mature OSS and famous architectures are the floor/evidence set, not the default destination.

Every high-impact target pressure-tests:

```text
H1 FLOOR
H2 FRONTIER
H3 KEYFLOW SYNTHESIS
```

Innovation should normally emerge as stronger composition of KeyFlow's Business Graph, Genome, temporal history, authority, evidence, recovery and external-reality semantics—not novelty for novelty's sake.

## Multi-agent contribution rule

No agent's private conclusion is canonical merely because it wrote code or produced confident analysis.

When an agent completes material work, persist:

- evidence examined;
- conclusions reached;
- decisions actually accepted;
- unresolved questions;
- files/code changed;
- tests actually executed and results;
- branch + commit SHA;
- implications for journeys / constellations / kernels / active pools.

Claude Code and Kimi Code may later implement/review bounded work, but implementation agents must not silently redefine unresolved target architecture.

## Production implementation boundary

Production implementation remains read-only unless the canonical programme explicitly enters an implementation phase and the relevant scope is authorized.

A drafted `KF-EXEC-*` artifact can exist before that point. Its presence means:

`WE UNDERSTAND HOW THIS SLICE COULD BECOME ACTIONABLE`

not:

`THIS IS NOW THE PROGRAMME FRONTIER`.

## Historical blueprint rule

`KEYFLOW v3` and other source plans are product/architecture evidence, not infallible current specifications.

Preserve durable principles when still supported, including:

> Isolation is the build strategy. Seamless integration is the user-facing outcome.

Patch or supersede historical technical prescriptions when repository evidence and accepted architecture require it.

## Final target of the programme

The analysis programme should eventually support a comprehensive answer to:

```text
What is KeyFlowOS now?
What was it intended to become?
Where do its truths and ownership boundaries conflict?
Which journeys and kernels should remain distinct or converge?
What is the strongest coherent target architecture?
What must migrate, in what order, without losing live truth?
What proof ratchets establish the new invariants?
Which exact models, services, routes, workers, integrations, tests and migrations change?
How do Claude Code / Kimi Code execute and review that transformation without architectural drift?
```

## Emergency recovery

If context is about to expire before a normal checkpoint:

1. stop broad analysis;
2. persist a dense recovery packet covering exact continuation state, active pools, decisions, findings, contradictions, recommendations, open questions, methodology and unrecoverable gaps;
3. refresh the handoff/rollover files;
4. continue only after the fresh session passes Context Integrity Check.

Target invariant:

> Chats, threads and model sessions may expire. KeyFlowOS knowledge and forward working flow must not.
