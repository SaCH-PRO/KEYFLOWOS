## F223 — model-supplied confidence can convert a human quick-confirm requirement into autonomous execution

**Status:** VERIFIED CODE-LEVEL / GOVERNANCE-SEMANTIC FINDING

`AiOversightService.evaluate()` can return a Tier-2 decision with:

```text
allowed = true
requiresQuickConfirm = true
```

`evaluateAutoApproval()` then applies a separate high-confidence override:

```text
if confidence > 0.9 && tier <= 2
→ autoApproved = true
```

The returned object preserves the earlier `requiresQuickConfirm=true` flag, so the decision can simultaneously represent:

```text
autoApproved = true
AND
requiresQuickConfirm = true
```

`ConversationalAIService` consumes only `decision.autoApproved` plus a local `action.confidence > 0.75` threshold before executing the action through `FlowOrchestratorService.executeToolDirectly()`.

The confidence value is produced by the model in conversational JSON and is mapped into `ConversationalAction.confidence` without a typed/range validation boundary. The model-provided `requiresConfirmation` field is likewise not used as an execution gate.

Therefore an epistemic signal generated by the same model proposing the action can eliminate a human control requirement that governance had just declared necessary.

This is distinct from:

- F057 — risk tier is overly load-bearing in control selection;
- F064 — stale low-tier pending approvals can later timeout into autonomous approval;
- F067 — Flow quick-confirm is not bound to an immutable pending action;
- F084 — historical approval learning can increase standing autonomy.

F223 concerns **model confidence acting as control evidence**.

### Target law

```text
MODEL / CLASSIFIER CONFIDENCE
→ may affect epistemic quality, ranking, readiness or review priority
→ MUST NOT itself satisfy QUICK_CONFIRM / FORMAL_APPROVAL / ADMIN_APPROVAL

required control
→ satisfied only by valid ControlEvidence
   OR explicit standing delegation/policy that already removed that control requirement
```

Affected kernels: K3, K5, K8.
Affected journeys: J2, J5, J6, J15.

## F224 — MessageIntake executes material child effects before resolving the human approval that is supposed to authorize them

**Status:** VERIFIED CODE-LEVEL / AUTHORIZATION-ORDER FINDING

`MessageIntakeOrchestrator.buildPlan()` creates an `AiApprovalItem` for synthetic tool identity `message_intake_action` and sets the intake to `reviewing`.

The authenticated route:

```text
POST /communications/businesses/:businessId/message-intake/:intakeId/approve
```

is protected by `AuthGuard + BusinessGuard` and then calls:

```text
executePlan(businessId, intakeId, userId)
```

`executePlan()` does **not** resolve or validate the pending `AiApprovalItem` before effects. It sequentially executes plan children that can include:

- creating KeyInbox thread/message state;
- sending email/WhatsApp/SMS replies through `AiMessageSenderService`;
- creating commands;
- creating CRM follow-up tasks and assignments;
- writing CRM notes.

Only after all children complete does it call `resolvePendingApproval(..., 'approved', userId)`.

`AiOversightService.resolveApproval()` is where Membership and `maxApprovalTier` are checked. A STAFF/default-tier-0 member can therefore reach `executePlan()`, cause material child effects, and only afterward fail the Tier-2 approval check. The outer catch then marks the MessageIntake `error`; it does not undo already completed child effects.

This is stronger than a generic under-scoped route finding because the semantic order is inverted:

```text
EFFECTS
→ APPROVAL AUTHORITY CHECK
```

rather than:

```text
APPROVAL AUTHORITY / CONTROL EVIDENCE
→ CLEARANCE
→ EFFECTS
```

Related existing roots that remain canonical and should not be duplicated:

- F029/F036 — inconsistent human-authority semantics across approval surfaces;
- F032 — parallel governance regimes;
- F040 — executor mechanics are not themselves a clearance boundary;
- F068 — approval lacks universal exact-action fingerprint binding;
- F093/F110 — composite/parent governance must not obscure exact child actions;
- KF-REC-048 — recovery semantics after partial/uncertain execution.

### Target law

```text
exact pending action / bounded child set
→ resolve current human authority
→ consume required ControlEvidence
→ issue/verify exact-action Clearance
→ acquire execution ownership
→ perform child effects
→ record OutcomeEvidence
```

An approval resolver may not be used as post-hoc evidence for effects that already occurred.

Affected kernels: K2, K3, K5, K7, K8, K11.
Affected journeys: J2, J5, J15, J18, J25.
