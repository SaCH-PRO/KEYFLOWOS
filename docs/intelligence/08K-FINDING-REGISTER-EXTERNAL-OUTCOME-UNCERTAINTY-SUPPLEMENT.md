## F151 — Outbound provider calls collapse ambiguous network outcomes into retryable failure or terminal failure instead of `OUTCOME_UNKNOWN`

**Status:** VERIFIED CROSS-PROVIDER / EXTERNAL-REALITY FINDING

Two representative outbound communication paths fail in opposite ways around the same distributed-systems ambiguity.

### Gmail path

`TransactionalEmailService` retries a send after thrown errors.

`GmailService.sendEmail()` performs a state-changing HTTP POST to:

```text
POST https://gmail.googleapis.com/gmail/v1/users/me/messages/send
```

The provider `messageId` is only available locally after a successful response is received and parsed.

The MIME message generated by KeyFlow does not include a stable application-level `Message-ID`; its MIME boundary is regenerated using time.

If Gmail accepts the message but the response is lost/connection fails afterward, KeyFlow can observe an exception and issue another provider send without a known provider receipt or stable reconcilable effect identity.

Current semantics therefore allow:

```text
provider may have accepted effect
→ local result = exception
→ caller interprets failure
→ retry creates another send attempt
```

### WhatsApp path

Scheduled WhatsApp delivery first claims `SCHEDULED → SENDING`, then sends through Twilio or Meta with an outbound HTTP POST.

If `fetch()` throws after request transmission, the scheduled-dispatch catch path writes:

```text
WhatsAppMessage.status = FAILED
```

But a network exception does not prove that the provider failed to create/accept the message.

Current semantics therefore allow:

```text
provider may have accepted effect
→ local result = exception
→ local status = FAILED
```

### Root issue

The system lacks a first-class distinction:

```text
DEFINITE_FAILURE
vs
OUTCOME_UNKNOWN
```

for provider effects whose acknowledgement may be lost.

This is especially important before automatic retry, manual retry, cancellation or compensation.

### External reference properties

Google guidance distinguishes idempotent from non-idempotent retry safety and advises proving a state-changing request is safe to retry.

Twilio exposes asynchronous outbound message lifecycle status callbacks and recommends periodic reconciliation because callbacks can be missed.

Target law:

> If KeyFlow cannot prove whether an external side effect occurred, it must preserve the same logical effect identity and enter `OUTCOME_UNKNOWN` / reconciliation before issuing an unsafe duplicate effect.

Affected kernels: K7, K8, K9, K11.
Affected journeys: J5, J6, J9, J10, J14, J18, J23.

# Target state distinction

```text
ExecutionClaim acquired
→ provider request attempt
   ├─ definitive rejection before effect → RETRYABLE_FAILED / FAILED_FINAL
   ├─ provider receipt accepted → AWAITING_EXTERNAL / SENT_TO_PROVIDER
   ├─ final provider outcome → SUCCEEDED / FAILED_FINAL
   └─ acknowledgement uncertain → OUTCOME_UNKNOWN
                                  ↓
                         reconcile by provider identity,
                         callback, poll, ledger or domain evidence
```

`OUTCOME_UNKNOWN` is not a synonym for FAILED and must not automatically create a fresh effect identity.

No production implementation is authorized by this supplement.
