# AI Module — KEY, the model gateway, and the 286-tool registry

> This is the subsystem that *is* the product. `apps/server/src/modules/ai/**` is 142 tracked files / 58,155 lines (91 non-spec source files / 47,845 lines, plus 51 spec files / 10,310 lines). It contains three separable things wearing one module: (1) a **provider-agnostic LLM gateway** that fans requests across seven backends with fallback, BYOK, budget caps, circuit breakers and streaming; (2) a **tool-calling orchestrator** — one 6,640-line god-service holding a 282-case dispatch switch over a 286-tool registry, wrapped in a role/tier governance gate; and (3) a **long tail of "intelligence" services** — briefings, pattern detectors, schedulers, matchers, workload aggregators — that mostly hang off HTTP endpoints and `setInterval` timers rather than a real job system. Everything routed through the gateway is metered per-business in credits and dollars.

## How it works

**One door in, seven doors out.** Every LLM call in the entire server is supposed to go through [model-gateway.service.ts](apps/server/src/modules/ai/model-gateway.service.ts). Its `complete()` and `streamComplete()` take a `GatewayRequest` carrying a `businessId`, a `TaskCategory` (12 of them: `extraction`, `reasoning`, `tool-calling`, …), OpenAI-shaped messages and tool definitions. The gateway loads the business's `AiPreferences` out of `AiMemory` (category `settings`, key `ai_preferences`, 120s in-process cache), resolves a `ModelStrategy` from a static three-mode routing table (`balanced` / `premium` / `fast`), promotes the business's `preferredProvider` to primary if it is configured, filters the candidate chain against monthly budget caps, then walks the chain trying each provider in turn. Each attempt gets up to 2 retries with linear backoff; three consecutive failures open a per-provider circuit breaker for 5 minutes. Only OpenAI uses a real SDK — `callAnthropic`/`streamAnthropic` hit `https://api.anthropic.com/v1/messages` with raw `fetch`, and xAI, Kimi, Google Gemini, "native" and "opensource" (OpenRouter/Ollama) all reuse the `openai` SDK against a swapped `baseURL`. Anthropic gets a real translation layer: system messages hoisted to `body.system`, adjacent same-role messages merged, `tool` messages flattened into `[Tool result for …]` user text, OpenAI `function` tools rewritten to `{name, description, input_schema}` and `tool_choice` mapped `auto→auto / required→any / named→tool`.

**Cost is recorded twice, from two tables that disagree.** After a successful completion the gateway fires (unawaited) `recordCostFromResponse`, which emits a Langfuse trace + generation via [langfuse.service.ts](apps/server/src/modules/ai/langfuse.service.ts) and then writes an `LLMProviderCost` row through [llm-cost.service.ts](apps/server/src/modules/ai/llm-cost.service.ts). Separately, [ai-usage.service.ts](apps/server/src/modules/ai/ai-usage.service.ts) — which is what most callers actually use, via `trackAndComplete` / `trackAndStream` / `trackEmbedding` / `trackVision` / `trackAudio` — enforces a 120-calls-per-minute-per-business rate limit, checks plan credits through `SubscriptionsService`, maps the caller's `feature` string to a `TaskCategory` via `FEATURE_TASK_MAP`, and writes an `AiUsageLog` row. There are **three** independent `$/1k-token` tables in this slice and they do not agree (see *Wiring reality*).

**A chat turn.** `POST /ai/businesses/:businessId/flow/chat` (and the SSE twin `/flow/chat/stream`) lands in [flow.controller.ts](apps/server/src/modules/ai/flow.controller.ts) → `FlowOrchestratorService.chat()`. The turn does, in order: rate-limit check; attachment extraction through `DocumentIntelligenceService`; **crew resolution** via [role-engine.service.ts](apps/server/src/modules/ai/role-engine.service.ts) (`resolveCrew` scores 8 roles from route/focused-item/message/sign-off stickiness and staffs at most 3 hats, none out-ranking the primary); a 2-credit check; a `BusinessGraphService` snapshot; `AiMemory` context; a pgvector semantic-memory search; page context; blueprint section; onboarding directive; a **thalamus** pass (`CognitiveTriageService.triage`, zero model calls, six regex classifiers) that returns a tier — `reflex` / `standard` / `deliberate` — plus `maxTokens` and `temperature`; then `selectToolsForRequest`, which filters the 286 tools by the crew's allowlist (or by a `JobRoleEnvelope` when the caller is position-scoped) and caps the menu at 128 by keyword-scoring tool names against the message. On the `reflex` tier no tools are sent at all — the schemas are ~13k tokens, ~80% of an ordinary turn. The prompt is either `FLOW_SYSTEM_PROMPT` or the role/crew prompt, with `{{CURRENT_DATE}}` substituted by `currentDateForPrompt()` (truncated to the *hour*, deliberately, so the prefix is stable), then `withEvidenceDiscipline()` appends `KeyCortexExpertiseLensService.EVIDENCE_DISCIPLINE`, then `buildPerceptionSection()` appends what KEY *observed* (via `UnifiedMemoryRetrievalService`, budgeted at a 1,200 ms deadline and skipped entirely on reflex).

**Then the gate.** Whatever tool calls come back are each passed to `AiOversightService.evaluate(businessId, toolName, mode, crew, envelope)` in [ai-oversight.service.ts](apps/server/src/modules/ai/ai-oversight.service.ts). That resolves the tool's risk tier (1–4) from the registry, loads `AutopilotSettings`, clamps it by `applyCrewCeiling` — a MIN over the crew members that actually grant *this* tool, never a MAX — and returns one of: blocked, auto-execute, quick-confirm, formal approval, or admin approval. Tier 4 is a hard stop unless autonomy ≥ 5 *and* a live `AuthorityGrant` *and* the tool is pre-approved. Blocked and approval-needed calls short-circuit into an `AiApprovalItem` and a text reply; auto-approved calls run through `executeTool` → `executeToolAction`, a 282-case `switch` that dispatches into roughly 60 other modules' services, most of them resolved lazily through `ModuleRef` to dodge circular module deps. Results are wrapped by `wrapToolResult` (changed entities + follow-on suggestions + family + tier), fed back to the model for a natural-language summary, persisted to a `FlowSession` scoped by `{businessId, userId ?? null}`, and passed to `enforceDoNotSay()` (which turns brand-voice violations into `learned_corrections` memory rows that the *next* prompt reads) and to `ConversationGenomeExtractorService` (pending genome signals).

**The background half.** `AiListener` mirrors 44 domain events into an in-memory array and invalidates the business-graph cache on 7 of them. `AgentTriggerService` hooks `EventEmitter2.onAny` and matches every non-`plan.*` event against `AgentTrigger` rows, forwarding to `JourneyOrchestratorService` (16 hardcoded templates in [journey-templates.ts](apps/server/src/modules/ai/journey-templates.ts)) and into `PlannerService` → `PlanExecutorService`. `PlanExecutorService` polls every 30s, plus `@OnEvent('plan.approved')`, and pushes steps onto BullMQ through [queue.service.ts](apps/server/src/modules/ai/queue.service.ts) (queues `ai-plan-steps` and `ai-cron-triggers`), whose worker re-checks governance, dispatches via `ActionDispatcherService` (circuit breaker + idempotency key + undo registration + feedback loop), and marks `AiPlanStep` rows. `CronSchedulerService` seeds BullMQ repeatable jobs from `AgentTrigger.schedule` on boot. Five more services run on bare `setInterval`: agent health (5m), connector scan (5m), pattern detection (15m), pro-auto monitor (15m), usage-alert dispatch (5m), match refresh (1h).

**Code execution.** `execute_custom_logic` reaches [code-executor.service.ts](apps/server/src/modules/ai/code-executor.service.ts), which runs a model-authored JS snippet either in a local `child_process` harness (`--max-old-space-size=128`, 15s hard timeout) or, when `E2B_API_KEY` + `PUBLIC_API_URL` are set, in an E2B cloud microVM. The microVM cannot carry a user JWT, so it calls back to the deliberately public `POST /code-executor/tool-bridge`, authenticated by a one-time 24-byte execution token that is minted per execution and deleted in a `finally`. Max 10 tool calls per snippet, `execute_custom_logic` itself blocked from recursion.

## Wiring reality

`AiModule` is imported by `app.module.ts:155` and by 25 other modules, so the module itself is unambiguously live. Within it, most things are genuinely reachable. What follows is what is not, each with the grep that establishes it.

**1. Three providers are registered on every boot and are in no module.** `KeyAuditorService` ([key-auditor.service.ts](apps/server/src/modules/ai/key-auditor.service.ts):19), `KeyMonitorService` ([key-monitor.service.ts](apps/server/src/modules/ai/key-monitor.service.ts):31) and `KeyPlannerService` ([key-planner.service.ts](apps/server/src/modules/ai/key-planner.service.ts):13) are `@Injectable()` classes with full spec files and **zero references outside their own file and spec** — they are not in `ai.module.ts`'s `providers`, so Nest never even constructs them. `grep -rn "KeyMonitorService" apps/server/src` returns only `key-monitor.service.ts` and `key-monitor.service.spec.ts`. Two of the three are already on the acknowledged ledger in `core/config/unreachable-provider.spec.ts:54-55`; `KeyMonitorService` is not, and escapes the gate because that check treats "any method name called anywhere" as reachability and `KeyMonitorService` has generic method names. 690 lines with 20 passing assertions, all against code Nest does not instantiate.

**2. `CapabilityModelService` is registered, exported, and injected by nobody.** `grep -rn "CapabilityModelService" apps/server/src apps/web/src` returns exactly three hits, all in `ai.module.ts` (lines 20, 118, 179). Nothing constructs it, no controller exposes it, the web never asks for it. It is the loader for the 4,729-line generated `capability-map.seed.ts`, which means **4,891 lines of this slice (10% of its non-spec source) is a data file plus a reader that nothing reads**. `capability-map.service.spec.ts` tests it directly with `new`.

**3. `ChaserService` — the docstring lies.** [chaser.service.ts](apps/server/src/modules/ai/chaser.service.ts):5 says "Runs daily (8am business timezone) or on demand". `grep -c "setInterval\|OnModuleInit\|@Cron\|@OnEvent" chaser.service.ts` → `0`, and `chaseBusiness` has no caller. It is provided and exported by `ai.module.ts` and has never executed. Already acknowledged in `unreachable-provider.spec.ts:50`.

**4. `CapacityInsightService` has the same docstring/reality gap, unacknowledged.** [capacity-insight.service.ts](apps/server/src/modules/ai/capacity-insight.service.ts):3 says "detects operational problems every 15 minutes". It has no timer, no lifecycle hook, no event handler (`grep -c` → `0`). Its only caller is `ai.controller.ts:1658` — a `GET` endpoint. It runs when a human loads a page, never on a schedule. Same for `TaskRebalancerService` and `TaskPrioritizerService`, whose docstrings describe autonomous behaviour and whose only entry is an HTTP route.

**5. `MorningBriefingService` says so itself.** [morning-briefing.service.ts](apps/server/src/modules/ai/morning-briefing.service.ts):48 — *"Briefing cron is managed per-business via AutopilotSettings. A separate scheduler would register them; for now, we provide manual generation."* There is no such scheduler. The briefing only exists when someone calls `GET /ai/businesses/:id/briefing/morning`.

**6. `KeyCommandService.enqueue()` and `.execute()` are fabricated-success stubs, and one of them is on a live path.**

```ts
// key-command.service.ts:536
async enqueue(job: {...}) {
  const id = `job_${Date.now()}_${Math.random().toString(36).slice(2, 8)}`;
  this.logger.log(`[enqueue] ${job.type} ${id}`);
  return { id, type: job.type, status: 'queued' };   // nothing was queued
}
```

`enqueue` has three callers, all in `key-cortex/key-cortex-actions.service.ts` (lines 562, 580, 710). Two of them write a database row first and then return success to the model:

```ts
// key-cortex-actions.service.ts:552-565
const report = await prisma.report.create({ data: { ..., status: 'generating' } });
await (this.commandService as any).enqueue({ type: 'GENERATE_REPORT', payload: {...} });
return { success: true, data: { reportId: report.id, status: 'generating' } };
```

Same shape at line 569-583 for `flowExecution` with `status: 'running'`. So `Report` rows sit at `generating` and `FlowExecution` rows at `running` forever, and the model is told the job started. `execute()` (line 546) is worse and dead — it returns `{ success: true, type, result: command.payload }`, echoing its own input back as the result — but it has no callers. This is the exact defect family `tool-honesty-sweep.spec.ts` was written about, one module over from where that spec looks.

**7. Three disagreeing price tables.** Computed by parsing all three:

| Model | `model-gateway.service.ts` | `llm-cost.service.ts` | `ai-usage.service.ts:936` (vision only) |
|---|---|---|---|
| `gpt-4o` | 0.0025 / 0.010 | **0.005 / 0.015** | **0.005 / 0.015** |
| `gpt-4o-mini` | 0.00015 / 0.0006 | **0.0004 / 0.0016** | **0.0004 / 0.0016** |
| `claude-3-5-haiku-20241022` | 0.0008 / 0.004 | **0.001 / 0.005** | — |
| `gemini-2.0-flash`, `gemini-2.5-pro` | present | **absent** | — |
| embeddings + audio (5 models) | **absent** | present | — |

The gateway's table carries a comment (line 255-262) explaining that gpt-4o was corrected *down* from the stale launch prices — and `llm-cost.service.ts` still holds those exact stale numbers, 2× and 2.7× high. Which one wins depends on the path: `recordCost` does `inputCost: input.inputCost || costs.inputCost`, so the gateway's number is persisted whenever it is non-zero, and `llm-cost`'s table only fires as a fallback and for the once-per-model warning. `model-pricing.spec.ts` guards the gateway table, `llm-cost-coverage.spec.ts` guards the llm-cost table, and **neither compares them to the other**.

**8. A contract-violating completion is paid for and never metered.** In `complete()`, `executeWithRetries` returns (tokens already spent, `recordProviderSuccess` already called), then `expectedContract` validation runs, and on failure it `throw`s at [model-gateway.service.ts](apps/server/src/modules/ai/model-gateway.service.ts):806-810 — **before** the `recordCostFromResponse` call on line 815. The `catch` in the candidate loop swallows it and tries the next provider. So a business on a strict contract can burn the full chain and record `$0` and no `LLMProviderCost` rows for any of it.

**9. `hasByokUpdate` omits Google, and the fallback encryption key is ephemeral.** [model-gateway.service.ts](apps/server/src/modules/ai/model-gateway.service.ts):2711-2718 checks `byokOpenai/byokAnthropic/byokXai/byokKimi/byokNative` and **not `byokGoogle`**, so a Google BYOK key can be saved with `BYOK_ENCRYPTION_SECRET` unset. In that case the constructor set `this.encryptionKey = randomBytes(32)` (line 640), so the ciphertext is written under a per-process random key, `safeDecrypt` fails after any restart and returns the raw ciphertext, and that ciphertext is sent to Google as the API key.

**10. The full `AiMemory` row set — including the BYOK blob — is readable over HTTP.** `RESERVED_MEMORY_CATEGORIES = new Set(['settings'])` at `ai.controller.ts:44` is enforced only in `assertMemoryCategoryAllowed`, which is called on the **write and delete** handlers. `GET /ai/businesses/:businessId/ai/memory` with no `category` query calls `this.memory.getAll(businessId)` (`ai.controller.ts:700`), and `AiMemoryService.getAll` (`ai-memory.service.ts:87`) filters only on `businessId` and expiry. The row `category: 'settings' / key: 'ai_preferences'` is returned with its `value` — a JSON blob containing `byok*` fields as `iv:authTag:ciphertext`. It is ciphertext, not plaintext, so this is not a key disclosure; it is nonetheless an encrypted-secret record crossing an HTTP boundary to every business member.

**11. One live web→server route mismatch.** `apps/web/src/app/app/control-tower/hooks/use-control-tower-ai-hub.ts:205` posts to `/ai/businesses/${businessId}/ai/execute` for the "Send Payment Reminders" tower action. `grep -rn "ai/execute" apps/server/src` returns **nothing**. That button 404s. I enumerated all 152 distinct route paths across the slice's 11 controllers and diffed them against 103 distinct web-side paths; this is the only genuine miss (the other 9 diffs are query-string artifacts of the extraction, e.g. `…/ai/plans${qs}`).

**12. MCP tool bridging is deliberately absent from the hot path.** [flow-orchestrator.service.ts](apps/server/src/modules/ai/flow-orchestrator.service.ts):1274-1291 documents that the bridging block was removed because it awaited `listBridgedTools` with a 10s connect timeout inline on every chat turn — harmless only because `selectToolsForRequest` had no callers at the time. `McpModule` is still imported by `ai.module.ts` and `McpClientManagerService` is still injected, but no MCP tool is advertised to the model.

**13. `AiListener.events` grows without bound.** [ai.listener.ts](apps/server/src/modules/ai/ai.listener.ts):14 declares `private readonly events: Array<{event, payload}> = []` and `processEvent` pushes every one of the 44 subscribed events into it forever. `getEvents()` has no caller. This is a slow memory leak proportional to total platform event volume.

**14. Unreferenced DTOs.** `CreateKeyCommandDto`, `ProfileChatDto` and `ProfileConfirmDto` have zero references outside their own files — `ai.controller.ts` types those bodies inline instead, which (per this repo's own `whitelist-masks-missing-tenant-checks` finding) means the payloads are never validation-pipe-stripped.

**What *is* solidly wired**, verified by grep rather than assumption: the gateway (28 external injectors), `AiUsageService` (56 external injectors), `FlowOrchestratorService` (chatwoot + phone-voice + 3 internal controllers), `AiOversightService` (7 external), the BullMQ workers (constructed in `onModuleInit`, `PlanExecutorService` and `CronSchedulerService` both enqueue), all 11 controllers (registered in `ai.module.ts:100`), `AiListener`, `PlanExecutorService`'s three `@OnEvent`s, `AgentTriggerService`'s `onAny` hook, and all seven `setInterval` schedulers. `ConversationalAIService` looked dead on a name grep but is injected at `connector-intelligence.service.ts:48` and called at line 347 — it is alive, contingent on `ConnectorIntelligenceService`, which is itself alive via its 5-minute timer and `commerce/drive-intake.controller.ts`.

## Tests

51 spec files, 10,310 lines. They are unusually good — most are named for a *defect* rather than a class, and several are architectural gates rather than unit tests.

**Gates that fail the build on structural regressions:**
- `flow-tool-honesty.spec.ts` — every one of the 286 declared tools has a handler case; `marketing_send_campaign` calls `sendCampaign` and not the no-op `markCampaignSent`; the five delegation loops resolve real row ids.
- `tool-honesty-sweep.spec.ts` — `commerce_send_invoice` binds and checks `delivery.status === 'FAILED'`; `schedule_action` (which promised future execution and had none) is deleted, tool and handler both; automations with no actions are created disabled.
- `handler-coverage-ratchet.spec.ts` — a shrink-only floor at 39% of the 282 handler cases named in some spec (measured 41%). Explicitly documents itself as an upper bound.
- `role-tool-reachability.spec.ts` — no tool is advertised to the model and refused by every role, with exactly two acknowledged destructive exceptions.
- `llm-cost-coverage.spec.ts` — every routable and every directly-invoked model has a price; no entry is zero/zero.
- `model-pricing.spec.ts` — mini < 4o on both axes by >5×, haiku < sonnet, output > input, the table carries a `LAST VERIFIED` date.
- `ai-usage-feature-coverage.spec.ts` — every `feature` string passed to `trackAndComplete` has a `FEATURE_TASK_MAP` entry (an unmapped feature silently bills at gpt-4o).
- `tool-enum-validity.spec.ts`, `flow-tool-registry.spec.ts`, `cortex-tool-bridge.spec.ts` — no duplicate names, no dotted names exposed to providers, every bridged target is a real organ tool, no phantom bridges.
- `prompt-cacheability.spec.ts` — the date token is hour-truncated at all four call sites, and a forward-looking guard that the role prompt (~327 tokens) is still below OpenAI's ~1024-token cache floor. Records the negative result that prompt caching is unavailable at this size.
- `governance-tools.spec.ts`, `contracts-reports-goals-tools.spec.ts` — tool enums are asserted equal to the DTO enums they bypass.

**Behavioural specs:** `ai-oversight-fails-closed.spec.ts` (an unreadable policy becomes `restricted`, not permissive defaults); `session-privacy.spec.ts` (14 assertions that an absent `userId` narrows rather than widens, and that saving never reassigns ownership); `key-identity-and-authority.spec.ts` (role authority clamps down, never up, and never mutates the cached settings); `role-crew.spec.ts` (crew is min-over-grantors, deterministic, ≤3 hats); `anthropic-stream-tools.spec.ts` (the streaming path maps tools to Anthropic shape and reassembles `tool_use` deltas); `provider-choice.spec.ts` (a preference promotes and never pins); `reflex-tier-cost.spec.ts` (reflex sends no tools on either chat path); `perception-join.spec.ts` (reflex pays nothing, retrieval is bounded and user-scoped); `deliberation-escalation.spec.ts`; `do-not-say-enforcement.spec.ts`; `learned-corrections-loop.spec.ts`; `invoice-send-delivery.spec.ts`; `tenant-scoped-update.spec.ts`; plus 12 per-domain tool specs (assets, deals, people, payments, portal, supplier, inventory, retainers, obligations, ledger reports, statement sources, governance) that mostly assert tenant scoping and "the handler returns what the service produced, not what it was asked for".

## Open questions

1. **Which pricing table is right?** The gateway's gpt-4o at $2.50/$10 per 1M matches the corrected figure its own comment cites; `llm-cost.service.ts` and the inline vision table both still carry $5/$15. Someone with billing data needs to pick one and delete the other two — and add a spec that compares them, since two specs currently guard the two tables independently and neither would notice the divergence.
2. **Is the 2024 model set deliberate?** Nothing in the code discusses upgrading past `gpt-4o` / `claude-3-5-sonnet-20241022`. If it is a cost decision it is unrecorded; if it is drift, the routing table is the single place to change it.
3. **Was `Report`/`FlowExecution` generation ever implemented anywhere?** `KeyCommandService.enqueue` is a documented "minimal stub" and there is no worker for `GENERATE_REPORT` or `EXECUTE_FLOW`. Whether the rows should be created at all before a real queue exists is a product call.
4. **`CapabilityModelService` — ship it or delete it?** 4,891 lines of generated model and loader with no consumer. The generator (`docs/architecture/capability-map/generate.js`) is presumably still run by hand; nothing here says what the seed is *for*.
5. **What surfaces `/ai/execute`?** The control-tower "Send Payment Reminders" button expects a governed tool-execution endpoint by that name. `POST /actions/businesses/:businessId/execute` in `graph-actions.controller.ts` does exactly that job with a `{toolName, args}` body — it is unclear whether the web call is simply pointed at the wrong path or whether a different endpoint was intended.
6. **Should the `settings` memory category be excluded from `getAll()`?** The write path already reserves it. I could not tell whether any consumer of `GET …/ai/memory` depends on seeing every row.
7. **Is `AiListener.events` used by anything out-of-process** (a debugger, a diagnostics route I did not find)? `getEvents()` has no caller in `apps/server/src`.
8. **Do the seven `setInterval` schedulers coordinate across replicas?** None takes a lock. In a multi-instance deploy every replica runs every scan; `pro-auto-monitor` and `connector-intelligence` both take actions, not just reads.
9. **`normalizeMessages` for Anthropic is an identity function** (`model-gateway.service.ts`:1924-1934 returns `msg` in both branches of its `if`). The real normalisation happens inside `callAnthropic`/`streamAnthropic`. Is the method a leftover, or was something meant to live there?
