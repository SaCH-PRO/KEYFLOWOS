Below is an implementation-grade overhaul document for KeyflowOS, grounded in the repo structure and current product direction. I have written it so both you and an AI coder can use it as a working specification.
KEYFLOWOS OVERHAUL MASTER DOCUMENT
Building an AI-Native Business Operating Intelligence System
0. Executive Summary
KeyflowOS should evolve from a broad business-management platform into a focused, AI-native Business Operating Intelligence System for service-led businesses.
The app’s mission should be:
Help business owners leverage time, money, people, and customer relationships through unified operational intelligence.
KeyflowOS should not try to be another CRM, invoice tool, booking app, content scheduler, or generic AI assistant. Its best-market position is as an integrated system where every customer, transaction, booking, payment, quote, calendar event, store interaction, and AI conversation improves the business’s operating intelligence.
The existing repo already supports this direction structurally. It is a pnpm monorepo with apps/web for the Next.js frontend, apps/server for the NestJS backend, packages/db for Prisma/Postgres, packages/api for shared tRPC/API contract, and packages/ui for shared UI primitives and Storybook. The previous repo audit confirms this architecture and identifies the major current surfaces: Cockpit, CRM, bookings, commerce, automations, projects, expenses, reports, documents, marketing/social, community, learning, marketplace, settings, auth, public booking, public payment, and order routes. 
The app also already has a large backend module system: identity, CRM, commerce, bookings, social, automation, site, AI, flow, gamification, webhooks, API keys, uploads, autopilot, notifications, payments, subscriptions, projects, expenses, reports, email marketing, lead forms, templates, education, community, marketplace, supplier, documents, Google Drive, diagnostics, and communications. 
The strategic issue is not lack of features.
The issue is feature entropy.
The overhaul must compress the product around a smaller number of powerful, interconnected systems:
• Business Blueprint Engine
• Storefront, Catalog, Quotes, Invoices, Payments, Inventory, Accounting Lite
• Relationship Intelligence / Advanced Contacts
• Timeline Calendar / Business Event Ledger
• KEY AI Native Orchestrator
• KeyflowOS Intelligent Store / Procurement Engine
• Clean Frontend-to-Backend Architecture and Code Health
Everything else should either be removed from MVP or placed under “Coming Later.”
1. Product Philosophy
1.1 Core Principle
Every module must answer this question:
Does this feature help the user leverage time, money, people, or relationships?
If not, it should be removed, hidden, or deferred.
1.2 System Principle
Every meaningful user action should produce structured operational intelligence.
Examples:
• A contact inquiry updates lead intelligence.
• A quote view updates conversion intelligence.
• An invoice payment updates financial intelligence.
• A missed booking updates reliability intelligence.
• A repeat customer updates relationship intelligence.
• A product purchase updates catalog and inventory intelligence.
• A calendar event updates temporal intelligence.
• An AI interaction updates blueprint intelligence.
1.3 UX Principle
KeyflowOS should feel like:
“My business knows what is happening and tells me what to do next.”
The user should not feel like they are “using software.”
They should feel like they are operating from a command center.

7.5 Contact Intelligence Scoring
Create a deterministic scoring engine first, AI second.
Example:
type ContactScoreInput = { totalPaid: number; invoiceCount: number; unpaidInvoiceCount: number; bookingCount: number; cancelledBookingCount: number; daysSinceLastInteraction: number; quoteSentCount: number; quoteAcceptedCount: number; messageResponseRate?: number; }; export function calculateLeadScore(input: ContactScoreInput): number { let score = 50; score += Math.min(input.totalPaid / 100, 20); score += Math.min(input.bookingCount * 3, 15); score += Math.min(input.quoteAcceptedCount * 5, 15); if (input.unpaidInvoiceCount > 0) score -= 10; if (input.cancelledBookingCount > 0) score -= Math.min(input.cancelledBookingCount * 5, 20); if (input.daysSinceLastInteraction > 30) score -= 10; if (input.daysSinceLastInteraction > 90) score -= 20; const quoteConversion = input.quoteSentCount > 0 ? input.quoteAcceptedCount / input.quoteSentCount : 0; score += quoteConversion * 15; return Math.max(0, Math.min(100, Math.round(score))); } 
AI should interpret the score and generate recommendations, not be the only scoring engine.

9.4 AI Safety Execution Model
Never allow vague user instructions to directly trigger irreversible actions.
Use this pipeline:
Step 1: Interpret
Convert vague user input into structured intent.
Step 2: Ground
Fetch relevant business data.
Step 3: Plan
Generate action plan.
Step 4: Risk Classify
Classify action risk:
• low risk: read, summarize, recommend,
• medium risk: draft, create internal task, prepare quote draft,
• high risk: send message, charge payment, cancel booking, delete/archive records,
• critical risk: financial, legal, customer-facing irreversible actions.
Step 5: Preview
Show what KEY is about to do.
Step 6: Execute
Only execute according to permission tier.
Step 7: Log
Record AI action in event ledger and AI execution log.

12. Backend-to-Frontend Clean Architecture
12.1 Required Standards
The codebase should enforce:
• domain-based modules,
• typed DTOs,
• shared API contracts,
• schema/API/frontend alignment,
• no hidden business logic in UI components,
• no direct cross-module coupling where event bus should be used,
• no unlogged business-critical actions,
• no unguarded tenant access.
12.2 Domain Boundaries
Use these primary domains:
identity blueprint contacts commerce calendar/timeline storefront key-ai procurement notifications settings 
12.3 Frontend Structure
Recommended:
apps/web/src/ app/ app/ cockpit/ contacts/ commerce/ calendar/ storefront/ key/ settings/ components/ cockpit/ contacts/ commerce/ calendar/ storefront/ key/ shared/ lib/ api/ client.ts contacts.ts commerce.ts calendar.ts blueprint.ts key.ts storefront.ts procurement.ts hooks/ schemas/ 
Break up the large apps/web/src/lib/client.ts noted in the audit as a future cleanup candidate. 
12.4 Backend Structure
Recommended:
apps/server/src/modules/ blueprint/ contacts-intelligence/ commerce/ timeline/ storefront/ key-ai/ procurement/ reports/ 
Existing modules do not need to be deleted immediately. Instead, consolidate user-facing flows around the new core domains.
12.5 API Health Rules
Every endpoint must:
• require business context unless public,
• validate DTO,
• verify membership,
• write timeline event if business-relevant,
• return typed response,
• avoid leaking cross-business data,
• include correlation ID in logs,
• avoid silent failures.
12.6 Event Logging Rule
Any of these actions must write to BusinessEvent:
• contact create/update,
• quote create/send/accept/reject,
• invoice create/send/pay/overdue,
• payment attempt/success/failure,
• booking create/update/cancel/complete,
• storefront publish/update/order,
• inventory movement,
• AI recommendation/action,
• procurement request,
• calendar scheduled action.
