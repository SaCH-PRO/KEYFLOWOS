## 1. Product Vision

### Module Name

**Relationship Intelligence**

### Core Promise

KeyFlowOS should not merely store contacts. It should help business owners know:

> Who matters, why they matter, what happened, what to do next, and how each relationship affects revenue, execution, opportunity, and growth.

Every contact can create one or more types of leverage:

1. **Money leverage** — revenue, sales, investment, paid work, purchasing power.
2. **Time leverage** — staff, contractors, suppliers, delegation, fulfillment, execution.
3. **People leverage** — referrals, introductions, hiring, partnerships, distribution.
4. **Knowledge leverage** — expertise, advice, mentorship, strategic insight.
5. **Credibility leverage** — endorsements, social proof, reputation transfer.
6. **Operational leverage** — vendors, logistics, service delivery, repeat processes.

The module should eventually behave like a **relationship operating system**, not an address book.

# 3. Core Gap Analysis

The module appears to have **breadth**, but likely lacks **coherence**.

The major risks are:

1. Too many fields without standardized meaning.
2. Too many flexible JSON fields without enforced taxonomy.
3. Lead/customer CRM bias instead of universal relationship intelligence.
4. Existing stats/highlights but not enough strategic dashboards.
5. Existing AI actions but not enough rule clarity, explainability, or safe execution.
6. Existing imports but possible weak deduplication, merge UX, and cleanup workflow.
7. Existing contact tasks but unclear follow-up operating rhythm.
8. Existing contact events but likely no canonical event taxonomy.
9. Existing source/status/segment fields but probably not standardized across industries.
10. Existing contact lists but not enough smart segments and saved views.
11. Existing cross-module links but likely insufficient UI surfacing.
12. Existing momentum/recommendation schema references, but unclear if fully implemented.

So the goal is:

> Turn scattered CRM capabilities into a polished, reliable, analytics-ready, AI-assisted Relationship Intelligence system.

# 7. Data Model Recommendations

The current model is already strong, but I would add a few fields carefully.

## 7.1 Contact additions

Add fields:

```prisma
relationshipType String? @map("relationship_type")
pipelineStage    String? @map("pipeline_stage")
priority         String? @default("NORMAL")
favorite         Boolean @default(false)
archivedAt       DateTime? @map("archived_at")
lastContactedAt  DateTime? @map("last_contacted_at")
nextActionAt     DateTime? @map("next_action_at")
nextActionType   String? @map("next_action_type")
relationshipHealth String? @map("relationship_health") // HOT, WARM, COLD, DORMANT, AT_RISK
```

You already have `leadScore` and `lastInteractionAt`, so do not duplicate those. 

## 7.2 Add or verify leverage model

Because `ContactMomentum`, snapshots, and recommendations are referenced in the `Contact` relations but not shown in full, verify their implementation. The `Contact` model already references `momentum`, `momentumSnapshots`, and `momentumRecommendations`. 

If not complete, implement:

```prisma
model ContactLeverageScore {
  id String @id @default(cuid())
  businessId String
  contactId String
  moneyScore Int @default(0)
  timeScore Int @default(0)
  peopleScore Int @default(0)
  knowledgeScore Int @default(0)
  credibilityScore Int @default(0)
  operationalScore Int @default(0)
  trustScore Int @default(0)
  engagementScore Int @default(0)
  totalScore Int @default(0)
  explanation Json?
  calculatedAt DateTime @default(now())
}
```

But if `ContactMomentum` already covers this, extend that instead of adding a duplicate model.

## 7.3 Opportunity model

If KeyFlowOS does not already have a dedicated opportunity/deal model, add one.

```prisma
model ContactOpportunity {
  id String @id @default(cuid())
  businessId String
  contactId String
  title String
  type String // SALE, PARTNERSHIP, REFERRAL, SUPPLIER, HIRE, INVESTMENT
  stage String
  estimatedValue Float?
  probability Int?
  expectedCloseAt DateTime?
  source String?
  lostReason String?
  notes String?
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

This is important because not all value is a quote/invoice. Some value is referral, supplier, investor, partnership, or contractor opportunity.

## 7.4 Communication consent

Existing `marketingOptIn` and `doNotContact` are good.  Add channel-specific consent later:

* emailOptIn
* smsOptIn
* whatsappOptIn
* consentSource
* consentAt

Do not overbuild this now unless you are ready for full compliance workflows.

## 10.2 Momentum

Track whether the relationship is:

* Improving
* Stable
* Cooling
* Dormant
* Recovering
* Converted

Potential logic:

* New positive event: + momentum
* No activity after due follow-up: - momentum
* Quote sent but no reply: at risk
* Repeat revenue: strong
* Task overdue: friction
* No interaction for X days: decay

## 10.3 Next-best-action rules

Examples:

### Follow-up

If contact is lead/prospect and last interaction > 3 days:

> Follow up with this contact.

### Quote follow-up

If quote sent and no invoice/payment after 5 days:

> Follow up on quote.

### Payment reminder

If invoice overdue:

> Send payment reminder.

### Referral ask

If customer paid and has high satisfaction/proven value:

> Ask for referral.

### Re-engage

If customer had revenue but no interaction in 90 days:

> Reconnect.

### Supplier check

If supplier is high operational score and no update in 30 days:

> Confirm availability/capacity.

### Contractor delegation

If contractor has completed tasks and business has overdue tasks:

> Consider assigning work.

# 15. What I Would Tell the AI Coder

Give them this instruction:

> Do not start by randomly adding features. First audit the current CRM implementation against this master plan. Preserve existing schema and APIs where possible. Prioritize standardization, event logging, contact profile usability, command center intelligence, and analytics. Use migrations only where existing fields cannot support the Relationship Intelligence model cleanly. Every new recommendation must be explainable and logged. Every automated action must be approval-gated unless explicitly configured.

# 16. Acceptance Criteria

The module is “complete” when a user can do this:

1. Import 500 contacts.
2. Clean duplicates.
3. Classify contacts by relationship type.
4. See who matters most.
5. See what happened with each person.
6. Know who to follow up with today.
7. Log calls/messages/meetings.
8. Create tasks and reminders.
9. Track quote/invoice/booking/payment history.
10. See revenue by source and contact type.
11. See dormant high-value contacts.
12. Get AI next-best-action suggestions with reasons.
13. Approve/deny AI actions.
14. Forecast revenue and workload from relationships.
15. Export/report CRM performance.
16. Use the system weekly without needing a spreadsheet.

That is the product-level definition of completion.

# 17. Final Recommendation

Yes — this may take months if built fully. But you can get a valuable MVP much sooner by focusing on the dependency chain:

**Taxonomy → clean contact profile → timeline → tasks/follow-ups → relationship scoring → command center → analytics → AI automation.**

The biggest mistake would be trying to build all 157 tasks as equal priority.

The correct move is to build a **Relationship Intelligence Core** first, then layer projections and automation on top.
