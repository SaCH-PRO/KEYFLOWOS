## First: the core UX problem you’re solving

Right now, the tension is this:

* You want **three different item types** (Products, Services, Packages)
* Users want to:

  * Browse *everything*
  * Understand differences instantly
  * Add **multiple mixed items** to one cart
  * Book only what *needs* booking
* Without:

  * Switching contexts
  * Getting lost
  * Hitting edge-case glitches

So the solution is **not more carousels**.

It’s **a unified browsing + filtering model** with *progressive disclosure*.

---

## Principle to anchor everything

### 🔑 **Unify items. Differentiate behavior.**

From the **user’s perspective**, everything is just an *item*.

From the **system’s perspective**, each item has:

* Type: product | service | package
* Purchase mode: instant | scheduled | mixed
* Fulfillment logic (delivery, booking, bundle logic)

**UX should never expose that complexity upfront.**

---

## Recommended Catalog Architecture (UI + Mental Model)

### 1️⃣ Replace “three carousels” with **one Catalog View**

Instead of:

* Products carousel
* Services carousel
* Packages carousel

Use:

### 🧠 **One master catalog grid or list**

With:

* Smart filters
* Visual type indicators

#### Example layout:

```
[ All ] [ Products ] [ Services ] [ Packages ]  ← filter tabs
[ Search 🔍 ] [ Sort ▾ ] [ Price ▾ ] [ Duration ▾ ]
----------------------------------------------------
[ Card ][ Card ][ Card ]
[ Card ][ Card ][ Card ]
```

Users:

* See **everything at once**
* Filter instantly
* Never feel like they’re “switching sections”

> Carousels are great for highlights, **terrible for exploration**

---

### 2️⃣ Use **Item Cards that encode behavior visually**

Every item card should answer 3 questions in under 1 second:

1. What is this?
2. How do I get it?
3. Can I add it now?

#### Card anatomy:

* Title
* Price
* 1–2 line description
* **Type badge** (icon + color):

  * 📦 Product
  * 🛠 Service
  * 🎁 Package
* **Primary CTA**

  * `Add to Cart`
  * or `Select Options`

No booking decisions yet.

---

### 3️⃣ Let the Cart handle complexity (not browsing)

This is critical.

### ❌ Don’t ask:

> “Do you want to book this now?”

### ✅ Instead:

> “Add it. We’ll sort it out later.”

---

## Cart Design (this is where you win)

### 🛒 Unified Cart, Mixed Items Allowed

Cart structure:

```
Your Cart
------------------------------------------------
📦 Product A        x2     $40
🛠 Service B        x1     Needs booking
🎁 Package C        x1     Includes 3 services
------------------------------------------------
Subtotal
```

Each item row has:

* Quantity controls (if applicable)
* “Edit details” (for services)
* Status indicator:

  * ✅ Ready
  * ⚠️ Booking required

---

### 4️⃣ Progressive Booking Flow (after cart, not before)

Once user hits **Checkout**:

#### Step 1: Review Items

* Products → ready
* Services → flagged
* Packages → expand to show contents

#### Step 2: Booking Step (only if needed)

* Group bookings by business logic:

  * Same service → one booking
  * Different services → separate slots
* Pre-fill durations and constraints

User only sees booking UI **if their cart requires it**.

## Navigation Patterns That Prevent Glitches

### 🔍 Smart Search

* One search bar
* Returns all item types
* Chips show item type

### 🧭 Sticky Filters

* Always visible
* Never reset unless user clears

### 💾 Persistent Cart

* Floating cart icon
* Items saved across navigation
* Clear “X items added” feedback

---

## Optional but Powerful Enhancements

### ⭐ Quick Add Mode

* “+” button on cards for power users
* Long-press or hover → quick add

### 🧩 Package Expansion Preview

* Hover or tap:

  > “Includes 2 services + 1 product”

### 🧠 Recently Viewed / Recommended

* Based on browsing, not purchases
* Keeps users moving forward

## Technical Insight (important for glitch prevention)

From an engineering standpoint, model everything as:

```json
Item {
  id
  name
  type: product | service | package
  requires_booking: boolean
  components?: Item[]
  price
  rules
}
```

The UI **never branches by type**.
Behavior is rule-driven, not hardcoded.

This is what keeps it stable at scale.

That’s how Amazon, Airbnb, Shopify, and ClassPass avoid UX chaos.
